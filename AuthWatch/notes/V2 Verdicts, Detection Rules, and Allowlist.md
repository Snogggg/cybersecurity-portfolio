
# AuthWatch v2: Verdicts, Detection Rules, and Allowlist

## What changed from v1
v1 only **counted** failures per source IP and per username. v2 adds a **verdict, a priority, and the reasons** for each source IP. It reads the pattern, not just the number, so a mistyped password and a brute-force attempt no longer look the same.

AuthWatch only **reads logs**. It can't block anyone. A verdict tells an analyst where to look first.

## Detection rules
Thresholds sit at the top of `authwatch.py` because they are heuristics, not standards. A busy public server would need different numbers.

| Rule | Trigger | Priority |
|---|---|---|
| Success after a long streak | 10+ failures on one account, then a success | **CRITICAL** (likely compromise) |
| Success after several failures | 3 to 9 failures, then a success | **HIGH** (review) |
| Fast volume | 15+ failures inside 60 seconds | **HIGH** (likely brute force) |
| Low and slow | 10+ failures spread over 1+ hours, never fast | **MEDIUM** |
| Invalid usernames | 5+ failures, half or more on nonexistent accounts | **MEDIUM** |
| Typo | 1 to 2 failures, then a success | **INFO** |
| Anything else | A few failures, no success | **INFO** (low activity) |

Each verdict lists its reasons, for example "55 failures within 60s" or "90% of guesses hit nonexistent accounts (54/60)".

## What each signal means
- **Speed:** a machine is steady and fast, a human is irregular. Speed alone isn't proof. Five typos in 10 seconds followed by a success is still a typo.
- **Accounts tried:** invalid usernames are the strongest single tell. A human doesn't try `admin` on a box with no `admin` account.
- **First seen and last seen:** shows how long the activity lasted. Hours of steady attempts suggest low and slow.
- **Outcome:** a failure is an attempt. A **success after a streak** is the moment something may have actually happened, so it ranks highest.
- **No success** doesn't mean harmless. It means an attempt, so it ranks lower than a success after a streak. The report says "attempt only" in those cases.

## How I read it like an analyst
1. Start from **accepted logins** and trace backward through the failures that preceded them.
2. Check the **pattern** (speed, accounts, duration), not a single failure.
3. Confirm outside the log: IP reputation, whether the address is expected, and what the account did **after** logging in.
4. A log pattern suggests intent but doesn't prove it. A stale script with an old password can look like brute force.

## The allowlist
A log holds only an IP, not who owns it. `--allowlist` takes a file of known-good IPs (office, VPN, my own machine).

- An allowlisted IP gets its priority **lowered one level**. Nothing is hidden.
- It is **not** a free pass. If an allowlisted IP shows a success after a long failure streak, the priority is **not lowered**, because that is what a compromised trusted machine looks like.
- An unknown IP isn't flagged just for being unknown. It simply gets no discount.
- Limit: an allowlist only reflects what I put in it. A breached employee laptop still looks trusted, which is why behavior analysis matters as well.

## Usage
```
python authwatch.py samples\attack-auth.log
python authwatch.py samples\real-auth.log
python authwatch.py samples\real-auth.log --allowlist samples\allowlist.txt
python authwatch.py samples\attack-auth.log --top 5 --out report.txt
```

# AuthWatch v2: Problems and Weak Spots

## A. Problems in the code and structure

| # | Problem | Why it matters | Fix |
|---|---|---|---|
| 1 | **Known and unknown IPs aren't separated.** The allowlist only lowers priority by one level. The report is one flat list. | An analyst has to scan everything to find what's new. | Split the report into **Known sources** and **Unknown sources**, with unknown sources first. |
| 2 | **The allowlist is exact-match only (from the code).** No CIDR ranges (like `10.0.0.0/24`), no IPv6 handling. | A whole office or VPN range needs one line per IP. | Use Python's `ipaddress` module for ranges. |
| 3 | **A failure streak has no time limit (from the code).** Failures are counted per user until a success, with no gap reset. | One typo a month ago plus 9 failures today reads as a 10-failure streak, a false CRITICAL. | Reset the streak after a quiet gap (for example, 15 minutes). |
| 4 | **Only `Failed password` lines are counted (from the code).** `Invalid user` lines with no password attempt, `maximum authentication attempts exceeded`, and failed key logins are ignored. | An attacker who only probes usernames and disconnects is invisible. | Parse more event types. |
| 5 | **It reads one file.** Rotated logs (`auth.log.1`) and compressed logs (`.gz`) are skipped. | Older attacks fall out of view. | Accept several files and read `.gz`. |
| 6 | **Timestamps are fragile (from the code).** Classic syslog has no year, so December to January breaks. Mixing ISO and classic lines in one file would also crash the comparison. | Wrong ordering or a crash. | Normalize everything to timezone-aware UTC. |
| 7 | **Thresholds were tuned against data I wrote myself.** | The sample log has 4 clean stories, and real traffic is messy. The false-positive rate is unknown. | Test on real logs (a honeypot or a public VM) and tune. |
| 8 | **Batch only, text only.** | It reports after the fact and can't alert in real time or feed other tools. | Add JSON output and a watch mode. |

## B. How an attacker would get around it

| Weakness | How an attacker exploits it | Mitigation |
|---|---|---|
| **It is failure-centric.** | With a **stolen or leaked password** (phishing, credential stuffing, a breached laptop), there are **zero failures**, only one clean success. AuthWatch never examines successes that had no failures. This is the biggest gap and matches the "hack someone's account" case. | Build a **per-user baseline**: known IPs, usual hours. Flag a success from a **new** source. |
| **The typo rule can be mimicked.** | 1 to 2 failures then a success rates INFO, so an attacker can fail twice on purpose and look like a typo. | Judge by context (new IP, odd hour), not failure count alone. |
| **Thresholds are guessable (from the code).** | Staying at 14 failures per 60 seconds avoids the fast rule (limit 15). Low-and-slow needs 1+ hours, so about 14 per minute for 50 minutes (roughly 700 guesses) can pass unflagged against a real account. A streak of 9 before success rates HIGH, not CRITICAL. | Use several time windows and randomize or tighten thresholds. Add rate-based and total-volume rules. |
| **Distributed attacks.** | Analysis is per IP. A botnet sending 1 guess per IP against `alex` never trips a rule. The per-username table shows it but gives no verdict. | Add per-**username** verdicts (many IPs, one account). |
| **A compromised trusted host.** | An attacker who owns an allowlisted laptop attacks **from the trusted IP**. Only CRITICAL is protected from the discount, so a slow guesser or a HIGH case from that IP gets **lowered**. | Never discount findings that involve a success. Add per-user baselines so even trusted IPs are checked. |
| **Shared IPs.** | Allowlisting an office NAT address trusts everyone behind it, including a compromised guest device. | Prefer user-plus-IP pairs over IP alone. |
| **The allowlist file is editable.** | An attacker with a foothold adds their own IP, or a stale entry stays trusted forever. | Protect the file, add expiry dates, and review changes. |
| **Log tampering.** | An attacker with root edits or deletes `auth.log`. AuthWatch trusts whatever the file says. | Ship logs to a separate, append-only collector (a SIEM or remote syslog). |
| **Log poisoning (to test).** | The username is attacker-controlled and my regex takes the first `from <ip>` it sees. A crafted username might make the line **look like it came from another IP**, possibly an allowlisted one. | Test with a crafted username. Anchor the regex to the last `from ... port N`, and strip or flag odd usernames. |
| **Other doors.** | Only SSH password events are parsed. Attacks via `sudo`, `su`, the console, web apps, or stolen SSH **keys** that succeed are out of scope. | Add other sources and key-login events. |
| **Detection is after the fact.** | The attacker has time between the success and anyone reading the report. | Real-time alerting plus automatic response (fail2ban, account lockout). |

## C. The lesson
Failure counting only catches **noisy** attackers. The dangerous one is quiet: valid credentials, one login, from a place the account has never been used. The strongest fix is a **baseline of normal per user** (known IPs, usual hours, usual login method), so a success from an unknown source is itself a finding.

## D. Planned structure for v3
1. **Known vs. unknown sources:** two report sections, unknown first.
2. **Per-user baseline:** first-seen IP per account. A success from a new IP gets flagged even with zero failures.
3. **Per-username verdicts:** catch distributed attacks.
4. **Streak gap reset** and **multiple time windows**.
5. **Allowlist upgrades:** CIDR ranges, expiry dates, and no discount on any success-related finding.
6. **Parse more events:** invalid-user probes, max-attempts disconnects, key logins.
7. **Multiple files and `.gz` support.**
8. **Test the log-poisoning case** and fix the regex if it works.

- Biggest gap: v2 is failure-centric, so a stolen password (one clean success, zero failures) is invisible.
- Zero trust = no login is trusted by default; judge each on context. It does not mean alert on everything.
- AuthWatch covers "assume breach" only. Prevention (MFA, key-only SSH, least privilege) matters more.
- v3 check on every success: new IP for the account, unusual hour, impossible travel, new login method, success after a probe, privileged account.
- Baseline limits: can learn an attacker as normal, false positives from travel/VPN changes, needs history.
